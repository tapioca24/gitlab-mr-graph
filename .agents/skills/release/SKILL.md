# リリース

このリポジトリの既存の Release workflow を使って GitHub Release を公開する。
`$release` で変更内容を調査し、次のバージョンを提案する。ユーザーが提案したバージョンと対象コミットを確認して確定した後に、タグの作成・push と公開確認を実行する。スキルの呼び出しだけではバージョン確定や公開の許可とみなさない。調査・準備だけの依頼では push しない。

## 対象とバージョン

- リポジトリルートで [CONTRIBUTING.md](../../../CONTRIBUTING.md)、[release.yml](../../../.github/workflows/release.yml)、[build-release.sh](../../../scripts/build-release.sh) を確認する。配布処理は workflow に任せ、ローカルから `gh release create` は実行しない。
- `origin` の取得先・push 先がともに `github.com/tapioca24/gitlab-mr-graph` であることと、`gh` の認証・リポジトリへのアクセスを確認する。以降の `gh` コマンドは `--repo tapioca24/gitlab-mr-graph` を指定する。
- `git status --porcelain` で未コミット変更（未追跡ファイルを含む）があれば停止して伝える。自動コミット、stash、reset はしない。
- `git fetch origin main --tags` でリモートの状態を取得する。通常の対象は `origin/main` の先端。HEAD が一致しなければ停止して SHA と差分を伝える。ユーザーが対象コミットを明示した場合だけ、そのコミットが `origin/main` の履歴に含まれることを確認し、クリーンな作業ツリーまたは一時 worktree で検証する。ブランチの push やマージはこのスキルの範囲に含めない。
- リモートのタグと公開済みの正式 Release を確認する。前回リリースは、公開済み正式 Release のうち最大の `vMAJOR.MINOR.PATCH` のタグを基準にする。そのタグから対象 SHA までのコミットと実際の差分を読み、ユーザーから見た機能追加・修正・互換性への影響を判断する。コミットの `feat` / `fix` 表記だけで決めない。前回タグが対象の履歴に含まれなければ停止して伝える。
- 提案する番号の目安は次のとおり。複数の変更があれば最も大きい変更を採用し、上げた番号より下位の番号は 0 にする。
  - patch：不具合修正、互換性を保つ改善、ドキュメント・内部変更。
  - minor：互換性を保つ機能追加。`0.x` の開発段階での破壊的変更も minor として提案し、影響を説明する。
  - major：`1.x` 以降の破壊的変更。CLI の引数、利用手順、出力形式など、既存の利用者が変更を必要とするかを確認する。`1.0.0` への移行は安定版として公開できる根拠がある場合だけ提案する。
- 初回の正式 Release は `v0.1.0` を候補にする。形式は `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`。プレリリースはビルドスクリプトが受け付けない。新規候補は既存リモートタグと重複せず、最大バージョンより大きくする。未公開タグで候補が使われている場合はその状況も踏まえて提案する。ローカルだけのタグを採番基準にしない。
- 前回タグが対象 SHA と同じなら「リリース対象の新しいコミットがない」と伝え、新しいタグを提案しない。
- ユーザーが最初にバージョンを指定しても候補として扱い、変更内容との整合性を説明してから確定の確認を求める。

## 検証と公開

1. 対象 SHA で `make test check build` を実行する。失敗したら停止し、タグを作らず原因を報告する。リリースを通すためのコード変更は行わない。
2. 検証が成功してから、前回バージョン → 提案バージョン、対象 SHA、主な変更、番号を上げる理由、検証結果を簡潔に提示し、この内容で公開してよいかユーザーに確認する。返答が来るまでタグ作成・push は実行しない。無応答や待ち時間の経過を承認とみなさない。修正希望があれば候補を更新して再確認する。
3. 承認後も対象 SHA と作業ツリーが変わっていないことを確認する。リモートの main と対象タグを再確認し、通常対象の main が進んでいたら停止して伝える。バージョンまたは対象 SHA を変更する場合は、新しい内容で検証とユーザー確認をやり直す。同じバージョン・SHA に対する既存の承認は再度求めない。
4. 確定タグがローカルまたはリモートに存在する場合、指しているコミットを照合する。対象 SHA と違えば停止する。同じなら再作成せず、未 push のローカルタグはそのタグだけを push、リモートタグは公開確認へ進む。
5. 新規タグを作り、そのタグだけを push する。`release_version` と `release_sha` は検証済みの値を設定する。

   ```sh
   git tag "$release_version" "$release_sha"
   git push origin "refs/tags/$release_version:refs/tags/$release_version"
   ```

   `--tags` や force push は使わない。push がエラーになった場合はリモートのタグの有無と SHA を読み取り確認してから状況を報告する。既に同じ SHA のタグが届いていれば公開確認へ進める。

## 公開確認・失敗時

- `gh run list --workflow release.yml --branch "$release_version" --json databaseId,headSha,status,conclusion,url` で、タグと対象 SHA に対応する実行を探す。同じ SHA の別タグの実行や、CI workflow の成功で代用しない。
- 実行の検出と完了を合わせて最大 15 分待つ。30 秒程度の間隔で読み取り確認し、進行状況を伝える。完了前に成功扱いにしない。時間を超えたら実行 URL と現在の状態を報告して終了する。
- 失敗・キャンセルなら `gh run view` と失敗ログを確認し、原因と実行 URL を報告する。タグの削除・移動、別バージョンでの再公開、workflow の再実行は勝手に行わない。
- workflow が成功したら `gh release view "$release_version" --json url,tagName,isDraft,isPrerelease,assets` で正式公開と次の 5 ファイル（サイズが 0 より大きいこと）を確認する。
  - `gitlab-mr-graph_<version>_darwin_arm64`
  - `gitlab-mr-graph_<version>_darwin_amd64`
  - `gitlab-mr-graph_<version>_linux_arm64`
  - `gitlab-mr-graph_<version>_linux_amd64`
  - `checksums.txt`
- 再開や公開確認の依頼で既存タグが明示された場合は、そのタグの SHA と実行・配布物を読み取り確認する。公開済みなら追加の公開操作やバージョンの提案をせず既存 Release の URL を返す。未 push のタグを公開する場合は、バージョンと SHA の承認が既にあるか確認し、なければ検証とユーザー確認を先に行う。
- 成功時はバージョン、Release の URL、検証と配布物確認の結果を簡潔に返す。認証・通信エラーや公開物の不足は未完了として報告し、トークンを表示しない。
